# AGENTS.md

Reusable Terraform module. This file guides AI assistants and contributors. Write all documentation, comments, commit messages and
issues in English.

## Purpose
Creates firewall groups, zone-based firewall policies and port forwards on a UniFi gateway, with the `ubiquiti-community/unifi` provider.
The module contains no context-specific value: everything goes through variables. Networks and zones belong to `terraform-unifi-network`.

Design rules specific to this module:
- Policies refer to zones, networks and groups by name or key; the module resolves the IDs. A zone is looked up by name unless it is in `zone_ids`: a zone created
  in the same run does not exist at plan time, and the keys of `zone_ids` are known even when its values are not.
- **Policy order cannot be managed**: the controller appends a policy to its pair of zones and the API cannot reorder (the provider documents `index` as read-only). The module only
  guarantees that block policies are created after allow policies, with two resources (`allow`, `deny`) and a `depends_on`. Never promise more.
- `terraform test` cannot see creation order with a mock provider: removing that `depends_on` leaves every test green. After changing `main.tf`, check it by hand with
  `terraform graph` on an example that has an allow and a block policy: the deny policy must depend on the allow one.
- `create_allow_respond` defaults to true for ALLOW policies except icmp and icmpv6 (the controller refuses it there). Other optional values stay `null` so the controller keeps its own.
- `regions` is only accepted on an external zone and must not be empty: the module validates the code format, not the zone, which it cannot know.
- `unifi_port_forward.enabled` is deprecated but a rule created without it is created disabled: always set it, and keep the deprecation warning documented rather than hidden.
- A single address in an address group has no `/32` (the controller refuses it). Group members are addresses or CIDRs, not ranges.
- Endpoints are built in `main.tf` in the shape of the provider (`matching_target`, `network_ids`, `ip_group_id`, `port_matching_type`...). An endpoint matches at most one of networks, group,
  ips or regions: a validation enforces it.
- The mock provider returns known IDs for data sources but not for resources: assert zone IDs that come from `zone_ids` or from the data source, never a group or policy ID.
- No test applies anything to a controller. A real check is a `terraform plan` against a controller, run by the owner, never an apply without their approval.

## Commands
- `terraform fmt -recursive`: format the code.
- `terraform init -backend=false && terraform validate`: validate the module.
- `tflint --init && tflint --recursive`: static analysis.
- `terraform test`: tests without real infrastructure (`command = plan` or `mock_provider`).
- `pre-commit run --all-files`: run everything at once, including `terraform-docs` and Trivy.

## Layout
`main.tf`, `variables.tf`, `outputs.tf` and `versions.tf` at the root, `examples/` (one directory per example), `tests/` (`*.tftest.hcl`).
Resources, data sources and locals stay in `main.tf`. Split by theme if the file grows, never by block type.
The inputs and outputs tables in `README.md` are generated by `terraform-docs`: do not edit them by hand.

## Code conventions
- `snake_case` names, without repeating the resource type. Use `this` for the single resource of a type.
- Every variable and output has a `description` and a `type`. Set `sensitive = true` on secrets. Set `nullable = false` when `null` makes no sense.
- Use `for_each` for collections and `count = var.enabled ? 1 : 0` for conditional creation, as the first line of the block.
- **No `provider` block in the module.** Declare `required_providers` with a lower bound only (`>= x`).
- Rename a resource with a `moved` block, never by destroying it.

## Versions
Never write code from memory of an old release. Before starting, and before each release:
- Check the latest stable versions of Terraform and of every provider (registry, GitHub releases) and read the changelogs since the version you know.
- Use the new features that apply (for example output `type`, Terraform 1.15) and say so in the commit message.
- The lower bound of a module is the oldest release that provides the features it really uses. CI tests the lower bound and the latest release.
- Examples and tests use current versions of the tools they mention (for example the current Talos release), not a version from memory.

## Tests
Every variable with a `validation` has an `expect_failures` test. Every optional feature has a test with and without it.
Tests never call a real API.

## Security
- No secret, state file, `.tfvars` or kubeconfig in Git. See `SECURITY.md`.
- No permissive resource "just to test" (firewall rules, permissions).
- Run `terraform plan` and get human approval before any `apply` in a live repository.

## Commits and versions
Conventional Commits: `fix:` (patch), `feat:` (minor), `feat!:` or `BREAKING CHANGE:` (major). Squash-merge into `main`.
`release-please` opens the release pull request, creates the SemVer tag and `CHANGELOG.md`. Never tag by hand.
